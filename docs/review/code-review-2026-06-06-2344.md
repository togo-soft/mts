## 严重 (Critical) — 必须修复

### C1. WAL `Write`/`WriteBatch` 与 `Close` 竞态 — 向已关闭文件写入

**文件**: `internal/storage/wal/wal.go:134-205`  
**影响**: 写路径关闭时触发 I/O 错误而非干净的 `ErrWALClosed`，可能导致数据损坏或 panic  
**详情**: `Write()` 先无锁检查 `w.closed.Load()`，再获取 `w.mu`。在此间隙 `Close()` 可完成文件关闭，导致 `w.seg.Write()` 向已关闭 fd 写入。

```go
func (w *WAL) Write(data []byte) (int, error) {
    if w.closed.Load() { return 0, ErrWALClosed }  // 无锁检查
    // ... 压缩 ...
    w.mu.Lock()   // Close 可能已经关闭了 seg
    defer w.mu.Unlock()
    // w.seg.Write() → 向已关闭文件写入
}
```

**修复方案**:
- 方案 A（推荐）: 获取 `w.mu` 后二次检查 `w.closed`，若已关闭则返回 `ErrWALClosed`
- 方案 B: 将 closed 检查和写操作放在同一把锁内（牺牲吞吐）
- 方案 C: 使用 `sync.RWMutex`，写操作用写锁，`Close` 用写锁，检查和写入原子化

---

### C2. `writeSSTableWithTimeout` goroutine 泄漏 + 孤儿文件

**文件**: `internal/storage/shard/shard.go:170-243`  
**影响**: 5 秒超时后 goroutine 继续执行 I/O；超时成功删除文件后 goroutine 可能重新写入同一文件形成孤儿  
**详情**: 超时时调用 `os.Remove(expPath)` 清理，但 goroutine 可能在此后完成写入，形成磁盘上的孤儿 SSTable。goroutine 持有的 `sstWriter` 和 file handle 也会泄漏。

**修复方案**:
- 方案 A（推荐）: 使用 `context.Context` + 取消机制，goroutine 在写前和关键点检查 `ctx.Err()`
- 方案 B: 超时时标记临时文件名（如加 `.aborted` 后缀），goroutine 完成后检查标记再决定是否保留
- 方案 C: 将写入改为同步 + 带超时的文件预分配模式，避免 goroutine 泄漏

---

### C3. `DeleteShard` TOCTOU 竞态 — 可删除新建 Shard 的数据

**文件**: `internal/storage/shard/manager.go:297-331`  
**影响**: 删除 shard 与创建 shard 之间存在竞态窗口，新写入的数据可能被 `os.RemoveAll` 销毁  
**详情**:

```go
m.mu.RLock()
_, recreated := m.shards[key]   // 检查 shard 是否仍存在
m.mu.RUnlock()
// ← 竞态窗口：GetShard 可在此处重新创建 shard 目录并写入数据
os.RemoveAll(dir)             // 删除新建 shard 的数据
```

**修复方案**:
- 方案 A（推荐）: 在 `m.mu.Lock()` 写锁保护下执行目录删除，或者引入 shard 级引用计数
- 方案 B: 为 shard 目录添加 `.deleting` 标记文件，`GetShard` 发现标记时拒绝创建，删除完成后再移除标记
- 方案 C: 使用 retry 标记，删除前先标记为删除态，新 GetShard 检查标记

---

### C4. `sstRefs.release` 静默忽略未知路径 — 引用计数泄漏

**文件**: `internal/storage/shard/shard_sstable_ref.go:52-59`  
**影响**: 未知路径的 release 被静默忽略，可能导致引用计数偏差，使 `IsSSTUnused` 在查询仍活跃时误报 true，导致 SSTable 被过早删除（数据丢失）  
**详情**: `release(path)` 查找 `sr.refs[path]`，若不存在直接 return。这允许了以下场景：`acquire` 失败但调用方仍执行 `release`，或路径不匹配（如绝对/相对路径），引用计数从不递减。

**修复方案**:
- 方案 A（推荐）: `release` 对未知路径记录警告日志，排查调用链；同时增加 `debug` 模式断言
- 方案 B: 将 acquire/release 改为返回 `ref` 对象（类似 `io.Closer`），确保配对
- 方案 C: 增加 `ref` 唯一 ID，确保 acquire 和 release 严格配对

## 高 (High) — 强烈建议修复

### H1. `SetSegmentNum` 非线程安全

**文件**: `internal/storage/wal/wal.go:503-505`  
**影响**: 并发 `SetSegmentNum` 与 WAL 写入可导致 segment 号冲突，数据错乱  
**修复**: 用 `atomic.Uint64` 或在 `w.mu` 保护下修改

---

### H2. WAL `normalize()` 强制开启压缩

**文件**: `internal/storage/wal/wal.go:62-63`  
**影响**: 用户设置 `Compressed = false` 被静默覆盖，无法关闭压缩  
**修复**: 移除强制覆盖，或增加 `ForceCompressed` 配置项；确保解压代码正确处理无压缩 header

---

### H3. `TriggerCompaction` 无限递归调用 — goroutine 持续创建

**文件**: `internal/storage/shard/shard.go:303-358`  
**影响**: 持续写入压力下不断创建 goroutine（虽有 semaphore 限流，但无退避）  
**修复**: 添加指数退避或最小间隔；或在 compaction 完成后检查 `NeedsCompaction` 再决定是否递归

---

### H4. `GetShard` 双重初始化 Compaction

**文件**: `internal/storage/shard/manager.go:82-109`  
**影响**: `NewShard` 已调用 `initCompaction`，`GetShard` 再次调用，且第二次使用不完整配置（缺少 `LevelCompactionCfg`、`SeriesStore` 等）  
**修复**: 移除 `GetShard` 中的二次 `initCompaction` 调用，或改为只在配置更新时才重新初始化

---

### H5. `Compact` 错误路径未清理输出文件

**文件**: `internal/storage/compaction/compaction.go:178-223`  
**影响**: 合并失败后保留部分写入的 SSTable 文件，浪费磁盘空间；虽被 `isSSTableComplete` 拒读，但可能干扰后续 compaction  
**修复**: 在 `Merge` 失败分支增加 `os.Remove(outputPath)`

---

### H6. `Compact` 持有 `cm.Mu` 执行 I/O

**文件**: `internal/storage/compaction/compaction.go:148-176`  
**影响**: 文件扫描（`CollectSSTables`）期间持有全局锁，阻塞 `SetConfig`、`GetProgress`、`ShouldCompact`  
**修复**: 锁内只做状态检查和 SSTable 列表快照，文件 I/O 在锁外执行

---

### H7. `channelIterator.Close()` 可无限阻塞

**文件**: `internal/query/iterator.go:73-80`  
**影响**: 若 producer goroutine panic 或卡死，`Close()` 永远不返回  
**修复**: 添加 context 超时或 deadline 支持；或使用 `tryRecv` 非阻塞退出

---

### H8. WAL `Replay` 静默跳过错误

**文件**: `internal/storage/wal/wal.go:516-567`  
**影响**: 段 header 读取失败只记日志继续，record 读取失败也静默跳过，数据丢失无感知  
**修复**: 增加 `ReplayOption`（如 `StopOnError`），至少返回统计信息（已跳过多少条）让调用方感知数据丢失

---

### H9. WAL `Close` 未等待 sync goroutine 退出

**文件**: `internal/storage/wal/wal.go:454-484`  
**影响**: `Close()` 关闭 `syncDone` channel 但未 wait goroutine，可能向已关闭 fd 执行 `fsync`  
**修复**: 添加 `sync.WaitGroup` 追踪 sync goroutine

---

### H10. WAL `CompressPayload` 空负载返回 `(nil, nil, nil)`

**文件**: `internal/storage/wal/compress.go:22-25`  
**影响**: 空输入返回全 nil，后续 `Write` 编码零长度 record，可能触发边界条件错误  
**修复**: 空负载返回错误或零长度标记，而非三重 nil

## 架构级建议

1. **WAL 并发安全重构**: `WAL` 结构体应统一并发模型 — 所有公共方法在锁内检查 closed 状态，`Close` 使用 `sync.WaitGroup` 等待所有进行中的写操作完成。

2. **Shard 生命周期管理**: 引入 Shard 级引用计数（如 `atomic.Int32`），`GetShard` 增加引用，`DeleteShard` 等引用归零后再删除目录。这是解决 C3 + C4 的根本方案。

3. **Compaction 锁粒度优化**: `Compact` 应在锁外执行 I/O 操作，锁内只做状态快照。考虑将 `cm.Mu` 拆分为读锁（查询状态）和写锁（修改状态）。

4. **资源泄漏巡检**: 为所有 goroutine 添加 `sync.WaitGroup` 或 `errgroup.Group` 追踪，确保 `Close` 路径等待所有后台 goroutine 退出。当前缺失 `WaitGroup` 的有：WAL sync goroutine、Shard compaction goroutine（使用 `errgroup` 但部分路径不 Join）。

5. **错误可观测性**: 当前大量 `slog.Warn` + `continue`/`return nil` 模式导致错误被静默吞掉。建议引入 `expvar` 计数器或 metrics 跟踪被跳过的 WAL records、失败的 compaction、引用计数异常等。

6. **测试覆盖建议**: 
   - WAL Write/Close 并发场景测试
   - Shard Delete + GetShard 并发测试
   - Compaction 失败路径测试（模拟 Merge 错误）
   - MemTable Full 背压端到端测试
   - 长期运行 goroutine 泄漏检测（`runtime.NumGoroutine`）
