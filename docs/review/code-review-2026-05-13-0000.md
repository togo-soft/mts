# microts MemTable 内存尖峰诊断报告

## 问题现象

大批量写入时，内存猛涨到 ~500MB，然后跌落到 ~200MB，随后又上涨。怀疑 memtable 没有及时 flush 导致数据在内存中堆积。

## 诊断结论

**核心问题：缺少双缓冲机制 + 同步阻塞 flush。** 这不是「flush 不及时」的问题，恰恰相反——flush 触发很及时，但它会阻塞整个 Shard 的写入，且 flush 过程中 SSTable 的编码/压缩产生了额外的内存峰值。

---

## 当前架构分析

### 数据写入路径

```
API → Engine.Write() → ShardManager.GetShard() → Shard.Write()
  → 1. s.mu.Lock()          ← 整个写入+flush 期间持有
  → 2. AllocateSID()
  → 3. PointToInternal()
  → 4. WAL.Write()
  → 5. memTable.Write()
  → 6. if ShouldFlush(): flushLocked()  ← 持锁执行，阻塞所有读写
  → 7. s.mu.Unlock()
```

### MemTable 结构

```go
type MemTable struct {
    mu      sync.RWMutex
    entries []types.InternalPoint  // 单一有序切片
    maxSize int64   // 64MB（估算：len(entries)*1024）
    maxCount int    // 3000
    // ...
}
```

### Flush 流程（全部在 `s.mu.Lock()` 持有下执行）

```
flushLocked():
  1. memTable.Flush() → 窃取 entries 切片指针，memtable 清空
  2. sstable.NewWriter() → 创建临时目录和文件
  3. w.WritePoints(points) → 逐点写入 per-field 列缓冲区
  4. w.Close()
     - 从临时文件读取原始数据
     - 逐 block 编码（delta/XOR/zigzag/bitmap/dict）
     - 逐 block 压缩（snappy/lz4/none）
     - 追加 CRC32C 校验和
     - 写入最终 .bin 文件
     - 清理临时目录
  5. triggerBackgroundCompaction()
```

## 根因分析

### 问题 1：同步阻塞 flush（最关键）

**现状**：当 `ShouldFlush()` 返回 true 时，`flushLocked()` 在当前 write goroutine 中同步执行，且持有 `s.mu` 写锁。

**后果**：
- SSTable 创建（编码 + 压缩 + 磁盘 I/O）可能需要 100ms-1s+
- 这期间该 Shard 的所有读写全部阻塞
- 其他 write goroutine 排队等待，各自持有待写入的数据

**对比 InfluxDB**：`WriteSnapshot()` 在后台 goroutine 执行，只短暂持有写锁做 `Snapshot()` 指针交换，写入路径几乎无感知。

**对比 VictoriaMetrics**：使用 active/passive memtable 双缓冲，passive memtable 在后台 flush，active memtable 继续接收写入。

### 问题 2：无双缓冲（active/immutable memtable）

**现状**：只有一个 memtable。flush 时：
- `Flush()` 窃取切片 → memtable 变空
- 但 `s.mu` 被持有，新写入被阻塞，所以「空 memtable 准备好接收新数据」这个事实没有意义

**后果**：flush 期间写入吞吐量降为 0（对该 Shard）。

### 问题 3：Flush 期间内存叠加

flush 期间同时存在：
- 被窃取的 entries 切片（~64MB 估算，实际取决于字段大小）
- SSTable Writer 的 per-field 列缓冲区（每个字段一个 `[]byte`，总大小 ≈ entries 原始数据量）
- Close() 时的编码缓冲区（逐 block 读取、编码、压缩）
- 临时文件在磁盘上，但读取时的 buffer 在内存中

**峰值 ≈ 2-3x memtable 大小（对单个 Shard）**

### 问题 4：粗粒度内存估算

```go
estimatedSize := int64(len(m.entries)) * 1024  // 假设每行 1KB
```

实际内存取决于字段值的类型和大小：
- 如果存大 JSON 字符串，每行可能是 10-50KB
- 3000 行 × 50KB = 150MB（远超 64MB 估算）
- `ShouldFlush()` 基于 count（3000）触发时，实际内存可能已经很大

### 问题 5：多 Shard 叠加

默认 `ShardDuration = 7天`。但如果写入覆盖多个 measurement，每个都有自己的 Shard 和 MemTable：
- 8 个 measurement → 8 个 memtable → 8 × 64MB = 512MB 基线上限
- 如果某个 measurement 的 flush 正在执行 → 叠加 SSTable 编码缓冲 → 更高峰值

### 问题 6：WAL segment 从不清理（磁盘问题）

`TruncateCurrent()` 和 `Purge()` 已实现但从未在正常流程中调用。注释说「由 compaction 模块负责」，但 compaction 代码中未见 WAL 清理调用。每个 segment 64MB，不会主动删除，只会在 `Open` 时打印警告。

## 业界方案对比

| 特性 | microts (当前) | InfluxDB v2 | VictoriaMetrics |
|------|---------------|-------------|-----------------|
| **内存结构** | 单一有序切片 | 分区哈希环 (16分区) | rawBlock (列式) |
| **双缓冲** | 无 | Cache.Snapshot() 原子交换 | active/passive memtable 对 |
| **Flush 方式** | 同步（持写锁） | 异步（后台 goroutine） | 异步（后台 goroutine） |
| **写入阻塞** | 是（flush 期间） | 极短（仅 Snapshot 交换） | 无（写 active，flush passive） |
| **Flush 触发** | 64MB/3000条/1分钟 | 25MB/10分钟空闲 | 可配置内存限制 |
| **背压机制** | 无（阻塞代替背压） | 1GB 硬限制+拒绝写入 | 内存限制+排队 |
| **WAL 清理** | 从不清理 | Snapshot 成功后清理 | 合并成功后清理 |
| **内存峰值** | flush 时 ~2-3x | snapshot 期间 ~2x | 近似 ~2x（但异步） |

## 优化建议

### 短期（低成本、高收益）

1. **WAL 清理**：在 `flushLocked()` 成功后调用 `s.wal.TruncateCurrent()`，清理已 flush 的旧 segment。不需要等 compaction。

2. **修复 MemTable Iterator 的并发安全隐患**：`Iterator()` 直接返回 `m.entries` 引用，如果在 `Read()` 持有 RLock 期间 `Flush()` 修改了 memtable（虽然当前因 shard 锁不会发生，但接口设计有隐患）。

3. **实际内存估算**：将 `estimatedSize = len(entries) * 1024` 改为 `unsafe.Sizeof` 或考虑字段实际大小。

### 中期（中等成本、核心收益）

4. **实现 active/passive memtable 双缓冲**：
   ```
   type MemTable struct {
       active  []types.InternalPoint   // 接收写入
       passive []types.InternalPoint   // 等待 flush（nil = 无待 flush 数据）
       flushing bool                    // 是否有后台 flush 进行中
   }
   
   Write():
     if passive != nil && !flushing:
         flushing = true
         go flushInBackground(passive)
     active = append(active, point)
   
   Flush():
     passive, active = active, nil  // 原子交换
     return passive
   ```
   写入路径不再阻塞于 SSTable I/O。

5. **异步 flush**：`flushLocked()` 改为：
   - 快速交换 memtable（持锁，<1μs）
   - 释放锁
   - 在后台 goroutine 执行 SSTable 写入
   - 期间新写入进入新的 active memtable

### 长期（高成本、架构优化）

6. **引入 VictoriaMetrics 风格的 rawBlock 列式内存格式**：内存中的数据直接以列式 block 格式存储，flush 时几乎零拷贝，避免「行→列」转换开销。

7. **批量写入优化**：`WriteBatch` 当前逐点调用 `Write()`（逐点加锁），应改为批量锁 + 批量 WAL 写入 + 批量 memtable 追加。

## 验证方法

1. 使用 `runtime.MemStats` 监控 `HeapAlloc` 和 `HeapInuse`
2. 在 `flushLocked()` 前后打印内存使用量
3. 使用 pprof 采集 heap profile：`curl http://localhost:6060/debug/pprof/heap > heap.prof`
4. 设置 `GODEBUG=gctrace=1` 观察 GC 周期
