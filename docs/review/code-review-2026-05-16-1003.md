## 🔴 问题一：无自动刷盘机制 → 背压死锁（根因）✅ 已修复

### 现象

写入达到 MemTable 容量上限后，`MeasurementWriter.Write()` 在背压循环中**无限等待**，因无任何 goroutine 自动触发刷盘。

### 触发路径

```
db.Write() → engine.Write() → MeasurementWriter.Write()
  → mw.memTable.ActiveFull() == true
  → for { time.Sleep(1ms) }  ← 永久挂起
```

### 根因分析

`ActiveFull()` 检查 `activeCount >= maxCount*2`，默认 `maxCount=50000`，即 100K 点触发背压。

当前系统中**没有任何自动刷盘触发机制**：
- `FlushCoordinator.FlushAll()` 仅在 `Engine.Close()` 和关闭信号中调用
- `FlushCoordinator.FlushWriter()` 仅被测试显式调用
- 写入路径自身不触发刷盘
- 不存在周期性刷盘 goroutine

**结果**：在 Windows 上（I/O 较慢或因杀毒软件延迟），WAL 和 SSTable 操作需更长时间，MemTable 更快填满并触发背压死锁。

### 影响范围

- `internal/storage/writer/writer.go:61-66` — Write 背压循环
- `internal/storage/writer/writer.go:121-126` — WriteBatch 背压循环
- 影响所有平台，Windows 上更易触发

### 证据

```
writer.go:61:  for mw.memTable.ActiveFull() {
writer.go:62:      time.Sleep(backpressureSleep)  // 1ms 无限循环
writer.go:63:      if mw.closed.Load() {
writer.go:64:          return fmt.Errorf("writer closed during backpressure wait")
writer.go:65:      }
writer.go:66:  }
```

`DefaultMemTableConfig()` 设定 `MaxCount: 10000`，`ActiveFull()` 在 2 万点时触发，无自动刷盘→死锁。

## 🔴 问题二：背压循环无超时保护

### 现象

`ActiveFull()` 循环仅检查 `closed` 标志位，无最大等待时间限制。如果刷盘机制失效（如当前情况），调用方永远阻塞。

### 修复方向

背压循环应加入超时机制：
```go
deadline := time.Now().Add(30 * time.Second)
for mw.memTable.ActiveFull() {
    if time.Now().After(deadline) {
        return fmt.Errorf("backpressure timeout")
    }
    time.Sleep(backpressureSleep)
    if mw.closed.Load() {
        return fmt.Errorf("writer closed during backpressure wait")
    }
}
```

## 🔴 问题三：Write 路径锁间隙导致 WAL 竞态

### 现象

`MeasurementWriter.Write()` 在**两次锁获取之间释放了 `mw.mu`**：

```go
// writer.go:68
mw.mu.Lock()
sid, err := mw.seriesStore.AllocateSID(...)
mw.mu.Unlock()  // ← 锁释放

// ... SID 分配完成到 WAL 写入之间有竞态窗口 ...

mw.mu.Lock()  // ← 重新获取锁
if mw.wal != nil {
    _, err := mw.wal.Write(walData)  // WAL 可能已被 Close
}
```

**竞态场景**：Writer A 释放锁等待 AllocateSID → Close() 被调用关闭 WAL → Writer A 重新获取锁尝试向已关闭的 WAL 写入 → 错误或 panic。

测试 `writer_test.go:832` 和 `engine_extra_test.go:946` 明确覆盖了此场景。

### 影响

非 hang 问题但有数据丢失风险。WAL 已关闭但仍接受写入，数据仅存于 MemTable 无持久化。

## 🟡 问题五：无周期性自动刷盘调度

### 根因

项目架构中 `FlushCoordinator` 负责编排 Writer → Flusher 流程，但：
- 无 `StartPeriodicFlush()` 方法
- 无基于 MemTable `ShouldSwap()` 的自动检查 goroutine
- 无基于时间间隔的自动刷盘

### 修复方向

`FlushCoordinator` 应新增周期性检查 goroutine：
```go
func (fc *FlushCoordinator) StartPeriodicCheck(interval time.Duration) {
    go func() {
        ticker := time.NewTicker(interval)
        defer ticker.Stop()
        for {
            select {
            case <-ticker.C:
                fc.checkAndFlush()
            case <-fc.stopCh:
                return
            }
        }
    }()
}

func (fc *FlushCoordinator) checkAndFlush() {
    fc.mu.RLock()
    defer fc.mu.RUnlock()
    for key, w := range fc.writers {
        if w.MemTable().ShouldSwap() {
            parts := strings.SplitN(key, "/", 2)
            if len(parts) == 2 {
                _ = fc.flushWriterLocked(parts[0], parts[1], w)
            }
        }
    }
}
```

## 🟡 问题六：数据目录结构冗余

### 现象

Shard 数据文件位于 `shardDir/data/sst_N.bin`，同时 SSTable Writer 生成到 `s.dir/data/sst_N.bin`（`writer_close.go`），而 `sstPath` 计算使用 `s.DataDir()` 即 `shardDir/data`。

`writeSSTableWithTimeout()` 中：
```go
sstPath := filepath.Join(s.DataDir(), fmt.Sprintf("sst_%d.bin", seq))
// ... 写入完成后 ...
srcPath := filepath.Join(s.dir, "data", fmt.Sprintf("sst_%d.bin", seq))
if srcPath != sstPath {
    // rename...
}
```

`DataDir()` 返回 `filepath.Join(s.dir, "data")`，所以 `sstPath` 和 `srcPath` 实际相同，rename 永远不会执行。这是无害冗余但表明目录结构设计不清晰。

### 状态

⚠️ 待确认 — `NewWriter` 内部可能将文件写入不同子目录。

## 🔴 问题八：checkAndFlush 过于激进 → 写入性能劣化（TPS 100K+ 降至 6K) ✅ 已修复

### 现象

修复 hang 问题后，Windows 上写入 TPS 从 100K+ 骤降至 ~6K。

### 根因分析

问题五的修复 `StartPeriodicCheck(1s)` 调用 `checkAndFlush()`，内部使用 `ShouldSwap()` 作为刷盘触发条件。`ShouldSwap()` 在 `MaxCount`（默认 10K，测试用 3K）时即返回 true，导致**每秒一次的小批量 SSTable 刷盘**。

Windows 上每次 SSTable I/O 操作（fsync、mkdir、rename）都会被杀毒软件扫描，与并发 WAL 写入叠加后产生严重 I/O 竞争，TPS 从 100K+ 降至 6K。

### 修复方案

1. **MemTable 新增 `NearFull()`**：在 1.5x `MaxCount` 阈值触发（75% of ActiveFull），延迟刷盘触发以批量积累数据、减少 I/O 频率
2. **MemTable 新增 `IdleExceeded()`**：独立空闲超时检查，确保数据在写入停止后仍被持久化
3. **`checkAndFlush()` 改用 `NearFull() || IdleExceeded()`**：替代原有的 `ShouldSwap()` 触发逻辑

### 修改文件

| 文件 | 变更 |
|------|------|
| `internal/storage/memtable/memtable.go` | 新增 `NearFull()` 和 `IdleExceeded()` 方法 |
| `internal/storage/memtable/memtable_test.go` | 新增 `TestMemTable_NearFull`、`TestMemTable_NearFull_WhenFlushing`、`TestMemTable_IdleExceeded`、`TestMemTable_IdleExceeded_ZeroTimeout` |
| `internal/engine/flush_coordinator.go` | `checkAndFlush()` 改用 `NearFull() \|\| IdleExceeded()` |
