# Micro-TS 时序数据库代码检视报告

**检视日期**：2026-05-13
**检视范围**：全项目（~67,500 行 Go 代码，~80 个源文件）
**检视维度**：架构设计、存储引擎、压缩编码、并发模型、测试质量、代码规范、安全性

---

## 一、项目概览

Micro-TS 是一个 Go 语言实现的单机时序数据库，采用 LSM-Tree 风格的存储架构。核心特性包括：

- **双缓冲 MemTable**：Active/Passive 异步 Flush，写入不阻塞
- **列式 SSTable**：单文件多 Section 布局，支持块级索引和时间范围查询
- **多种压缩编码**：Gorilla XOR（Float64）、Delta-of-Delta（Timestamp）、ZigZag+Varint（Int64）、Bitmap（Bool）、Dictionary（String）
- **双策略 Compaction**：Size-Tiered（平坦）+ Leveled（分层），可独立启停
- **WAL 持久化**：支持 LZ4 压缩、段轮转、CRC32 校验
- **基于 SID 的标签编码**：标签字符串映射为 uint64，大幅减少 WAL/SSTable 存储开销
- **bbolt 元数据存储**：Catalog、SeriesStore、ShardIndex 三个子系统
- **gRPC 服务接口**

### 项目分层

```
cmd/server/          gRPC 服务入口
mts.go               公共 API 门面（Facade）
internal/engine/     引擎层：编排 Write/Query/Flush/Compaction 生命周期
internal/api/        gRPC 服务实现
internal/query/      跨 Shard 查询迭代器（堆归并）
internal/storage/
  shard/             Shard 容器（核心单元）：Write/Read/Flush/Lifecycle
    sstable/         列式 SSTable 读写与迭代器
    compression/     列编码器（delta, xor, varint, zigzag, bitmap, dict, bit_io）
  memtable/          Active/Passive 双缓冲内存表
  wal/               WAL 预写日志（段管理、LZ4 压缩、CRC32）
  compaction/        Size-Tiered + Leveled Compaction、Merge、Tombstone
  metadata/          bbolt 元数据（Catalog、SeriesStore、ShardIndex）
types/               Protobuf 生成类型 + 转换辅助函数
tests/e2e/           端到端测试套件（22 个测试场景）
```

## 二、架构优点

### 2.1 分层清晰，职责明确

- Engine 层纯粹做编排和路由，不包含存储逻辑
- Shard 是核心容器，通过接口（SeriesStore、SchemaStore、ShardAccess）解耦元数据层
- 公共 API（mts.go）是薄门面，内部包不对外暴露

### 2.2 双缓冲 MemTable — 写入零阻塞

```
Write → active（持写锁，极短临界区）
         ↓ 触发条件满足
      Swap() → active ↔ passive（持写锁，O(1)）
         ↓ 释放锁
      Flush passive → SSTable（无锁，耗时操作）
```

这是 LSM-Tree 写入路径的经典优化，实现干净利落。`ActiveFull` 反压机制（2x 阈值 + 主动触发 flush + 忙等）有效防止了内存无限增长。

### 2.3 SID 标签编码 — 核心空间优化

标签字符串不在 WAL 和 SSTable 中重复存储，而是通过 `SeriesStore.AllocateSID` 映射为 `uint64`。对于高基数标签场景，压缩比可达 10:1 至 100:1。标签→SID 映射持久化于 bbolt，崩溃恢复后可重建。

### 2.4 三阶段异步 Flush — 精细化锁管理

异步 Flush 分三个阶段，仅在阶段 1（WAL 轮转、MemTable Swap、预留 Seq）和阶段 3（ClearPassive、原子重命名、WAL 截断）持锁。阶段 2（SSTable 写入）完全无锁，写入路径不被阻塞。

### 2.5 列式 SSTable 双层索引

BlockIndex（时间范围 → 行偏移） + BlockSectionMap（Section → 块字节偏移），支持 O(log N) 时间范围定位 + 精确的字节范围读取。范围查询只解码匹配的块，列式存储提供字段级投影能力。

### 2.6 编码选择合理

| 类型 | 编码 | 适用场景 |
|------|------|---------|
| Timestamp | Delta-of-Delta + Varint | 均匀采样时间戳，二阶差分趋近 0 |
| Float64 | Gorilla XOR | 相邻浮点值低位变化，前导零/后导零压缩 |
| Int64 | ZigZag + Varint | 小整数/负数高效变长编码 |
| Bool | Bitmap | 1 bit/值，批量压缩 |
| String | Dictionary + 回退 Raw | 低基数字典高效，高基数自动回退 |

### 2.7 双 Compaction 策略互补

- **平坦 Compaction**（Size-Tiered）：小文件合并，适合低写入量。两阶段合并处理 >10 输入文件。
- **分层 Compaction**（Leveled）：类似 RocksDB，每层大小指数增长（L0:10MB → L4:100GB）。写放大可控，读放大降低。

两种策略互斥，分层优先。可独立启停，支持运行时切换。

### 2.8 并发模型成熟

| 组件 | 同步机制 | 评价 |
|------|---------|------|
| Shard | RWMutex + atomic.Bool(closed) | 读写分离，写优先 |
| MemTable | RWMutex + atomic.Bool(flushing) | 双缓冲 + CAS 漏斗 |
| WAL | Mutex + atomic.Bool(closed) | 64KB 缓冲 + 定期 fsync |
| Compaction | Mutex + atomic.Int32(compactInProgress) | 单 goroutine 串行 |
| SSTable Reader | 无锁（不可变文件） | 引用计数保护 |
| SeriesStore | bbolt TX + sync.Map 缓存 | 读快 TX 优先 |

### 2.9 错误处理务实

- WAL 打开失败不阻止 Shard 创建（软降级）
- 脏记录跳过（WAL Replay 中 CRC 失败 → log + continue）
- Compaction goroutine panic → log + recover
- Flush 失败 → MergePassiveBack 回退
- 每处 I/O 错误均有处理，使用 `_` 显式忽略仅在确定无害的场景

## 三、问题与改进建议

### 3.1 高优先级（影响正确性或性能）

#### 3.1.1 Shard.Read 全量加载 → 大数据集 OOM

**现状**（`shard_io.go:116-153`）：`Read(startTime, endTime)` 将全部 MemTable + 全部匹配 SSTable 的数据加载到内存切片中，然后 `sort.Slice` 排序。代码中已有注释承认此问题。

```go
// 将 MemTable 数据全部读出
for memIter.Next() { rows = append(rows, ...) }
// 将 SSTable 数据全部读出
for each SSTable { rows = append(rows, ...) }
// 全量排序
sort.Slice(rows, ...)
```

**建议**：使用 `query.QueryIterator` 中的堆归并模式替代全量加载。MemTable 和 SSTable 已按时间排序，只需 K 路归并而非全量排序。可节省 O(N) 内存和 O(N log N) 排序时间。

#### 3.1.2 QueryIterator 与 Shard.Read 功能重复

`QueryIterator`（`query/iterator.go`）实现了正确的跨 Shard K 路堆归并，但 `Shard.Read` 自己又做了一遍全量加载+排序。两条查询路径逻辑不一致：`Engine.Query` 走 QueryIterator → ShardIterator，而注释掉的代码暗示曾经有另一条路径。

**建议**：统一查询路径，淘汰 `Shard.Read` 的全量加载实现，或者在 `Shard.Read` 中也实现堆归并。

#### 3.1.3 WriteBatch 无原子性保证

**现状**（`engine_write.go`）：`WriteBatch` 是简单的 for 循环 `Write(point)`。无事务语义——部分写入成功、部分失败时无法回滚。

```go
func (e *Engine) WriteBatch(ctx context.Context, points []*types.Point) error {
    for _, p := range points {
        if err := e.Write(ctx, p); err != nil { return err }
    }
    return nil
}
```

**建议**：如果不需要原子 batch，应明确文档说明。如果需要，应在 WAL 层实现 batch 写入（已有 `WAL.WriteBatch` 方法），失败时截断 WAL 到 batch 前的位置。

#### 3.1.4 MemTable 乱序检测逻辑有缺陷

**现状**（`memtable.go:53-78`）：`Write` 中仅当最新写入乱序时才触发排序，但如果乱序点不是最后一个（例如前面某个点在最后写入后才发现乱序），则不触发排序。例如：[1, 2, 5, 3] —— 追加 3 时检测到 5 > 3，触发排序。但如果有 WAL Replay 恢复到已乱序的切片，且后续只有顺序写入，乱序就不会被纠正。

**建议**：改用插入排序维护有序性，或在每次 WAL Replay 后强制执行一次排序。

#### 3.1.5 generateFieldMap 字段检测并发不安全

**现状**（`writer_close.go:446-479`）：`detectFieldType` 基于「首次出现字段名」检测类型。该逻辑假设同一字段在所有行中类型一致，这在写入路径已验证类型的前提下是成立的。但如果在同一批次中字段先出现 float64 后出现 int64，可能产生意外的类型推断。

**建议**：在 Close() 时对已检测的类型做一致性校验，发现不一致时报错而非静默忽略。

#### 3.1.6 Tombstone 查找性能 O(n)

**现状**（`tombstone.go:25-33`）：`ShouldDelete` 对 tombstone 列表做线性扫描。在大量 tombstone 的 compaction 场景下，每个点 O(n) 的查找可能成为瓶颈。

```go
for i := range ts {
    t := &ts[i]
    if t.SID == sid && timestamp >= t.MinTime && timestamp <= t.MaxTime {
        return true
    }
}
```

**建议**：将 tombstones 组织为 `map[uint64][]Tombstone`（按 SID 分组），或使用区间树，将查找降为 O(log n)。

#### 3.1.7 SSTable Reader 无内存池/复用

**现状**（`reader_blocks.go`）：每次读块都分配新切片（make），无 sync.Pool 或预分配缓冲。在高并发读取下，GC 压力显著。

**建议**：对固定大小的块缓冲区使用 `sync.Pool`，减少 GC 分配。

### 3.2 中优先级（影响可维护性或扩展性）

#### 3.2.1 SSTable 写入中的字符串 Section 全量读取

**现状**（`writer_close.go`）：`encodePerBlock` 对字符串字典编码使用 `os.ReadFile` 读取整个 temp 文件到内存。在字符串字段占比较大的场景下（如日志类数据），会导致写入路径的内存峰值过高。

**建议**：对字符串 Section 也实现流式块读取，避免全量加载。

#### 3.2.2 Compaction 配置缺乏动态调整

**现状**：Compaction 配置在 Shard 创建时固化，无法运行时调整。层级配置（`LevelConfig`）硬编码为 5 级默认值。

**建议**：支持通过 API 查询和修改 compaction 参数（如 `UpdateCompactionConfig`），对运行时调优开放。

#### 3.2.3 WAL Replay 无断点续传

**现状**（`wal.go:439-473`）：WAL Replay 每次从第一个段的第一条记录开始。对于长期运行的 Shard，如果 WAL 段文件未被及时清理，重启后需要 Replay 大量已持久化的数据。代码注释也承认了这一点：

> "从开头重放所有 WAL 段是可靠且简单的"

**建议**：引入 WAL checkpoint 机制。在 SSTable Flush 完成后记录已持久化的 WAL offset/segment，重启时从 checkpoint 之后开始 Replay。

#### 3.2.4 缺少 Metrics/Telemetry

**现状**：项目中没有任何 metrics 暴露（Prometheus/expvar）。排查性能问题只能依赖外部 profiling。

**建议**：在关键路径添加 metrics：
- `write_latency_seconds`（写入延迟）
- `flush_duration_seconds`（Flush 耗时）
- `compaction_duration_seconds`（Compaction 耗时）
- `memtable_active_bytes`（Active 大小）
- `sstable_count_per_shard`（每 Shard 文件数）
- `wal_segment_count`（WAL 段数）

#### 3.2.5 gRPC 层缺少流式查询

**现状**（`api/grpc.go`）：QueryRange 是 Unary RPC，大数据集查询会导致客户端超时溢出。

**建议**：添加 Server-Side Streaming RPC，分批返回查询结果。

#### 3.2.6 Command-Line 工具缺失

**现状**：`cmd/server/main.go` 只是一个启动脚本。没有 CLI 管理工具（如创建 database、查看 shard 状态、手动触发 compaction）。

**建议**：使用 cobra 实现 `mtsctl` 管理工具。

### 3.3 低优先级（代码风格和工程实践）

#### 3.3.1 单个大文件可拆分

| 文件 | 行数 | 建议 |
|------|------|------|
| `sstable/writer_close.go` | ~480 | 按编码类型拆分为 `writer_close_ts.go`、`writer_close_field.go` 等 |
| `sstable/reader_blocks.go` | ~388 | 按解码类型拆分 |
| `compaction/level.go` | ~617 | 分离合并逻辑、选择逻辑、检查点逻辑 |
| `sstable/iterator.go` | ~350 | 为 block loading 和 row iteration 独立接口 |

**但是**：当前代码通过文件名后缀已做逻辑分组（`writer.go`、`writer_field.go`、`writer_close.go`），拆分不算迫切。

#### 3.3.2 部分测试覆盖可加强

- **catalog_impl.go** 无独立测试（仅通过集成测试隐式覆盖）
- **shard_index_impl.go** 无独立测试
- **Compaction Commit 失败路径**未测试（原子性验证）
- **Tombstone Compact 延迟清理**未测试
- 无大规模数据测试（>10K 点）
- `TestCompactionManager_shouldCompactLocked_True` 因竞态被跳过

#### 3.3.3 魔法数字需要常量化

**现状**：部分代码中存在未命名的数字：
- `shard_io.go`: `time.Millisecond`（反压等待）硬编码
- `merge.go`: `1000`（批量写入大小）、`0x9e3779b97f4a7c15`（去重哈希黄金比例）
- `wal.go`: `64 * 1024`（写入缓冲区大小）

**但大部分**代码已通过常量良好定义（`fieldPoolSize`、`blockSize`、`MaxSSTableCount` 等）。

#### 3.3.4 有限的注释策略可更加一致

**现状**：绝大多数代码注释简洁有效。但部分复杂逻辑（如 `shard_flush.go` 三阶段协议、`merge.go` 两阶段合并、`level.go` 层级选择算法）缺少高层次的过程说明。

**建议**：对核心算法（Flush 三阶段、Compaction 层级选择、XOR Float 编码）补充一两个段落的过程注释。

## 四、时序数据库专项评估

以 InfluxDB IOx、VictoriaMetrics、TDengine 等成熟 TSDB 为参照：

### 4.1 对标分析

| 维度 | Micro-TS | 行业基准 | 评价 |
|------|---------|---------|------|
| 写入路径 | MemTable + WAL | WAL → MemTable → Flush | 标准 LSM 模式 |
| 存储格式 | 列式 SSTable（单文件） | Parquet / TSM / 自定义列式 | 设计合理 |
| 压缩编码 | 7 种专用编码 | Gorilla / Delta / Dict | 覆盖全面 |
| Compaction | 双策略 | 通常一种（Leveled/Size-Tiered） | 灵活但复杂 |
| 标签索引 | SID 映射（bbolt） | 倒排索引 / TSFID | 中等规模合适 |
| 查询引擎 | K 路堆归并 | 向量化执行 / DataFusion | 功能完整但可优化 |
| 数据过期 | 整 Shard 删除 | 支持更细粒度（Series/Point级） | 粒度偏粗 |

### 4.2 时序特定问题

**下采样/聚合**：项目未实现时序数据的下采样（Downsampling）和自动滚动聚合（Continuous Aggregation）。这对于长期数据保留至关重要。

**基数估计**：SeriesStore 中 `SeriesCount` 通过 bbolt 遍历计数（`series_impl.go:247-262`），O(n) 扫描。大数据量下可能很慢。建议使用 HyperLogLog 或维护原子计数器。

**时间精度**：统一使用 int64 纳秒时间戳。这提供了纳秒精度但占 8 字节。对于秒级采样数据，压缩后通常很小（Delta-of-Delta ≈ 1-2 字节），设计合理。

**Tag 过滤**：QueryIterator 中的 tag 过滤是后过滤（读取全部数据后按条件筛除）。对于高选择性过滤（tag 匹配率 < 1%），应考虑在 Shard 层通过 bbolt tag 索引做前置过滤。

## 五、安全性评估

### 5.1 输入验证

| 检查项 | 状态 | 说明 |
|--------|------|------|
| gRPC 输入校验 | 部分 | `api/grpc.go` 对 nil check 做基本校验，但未校验字段值范围 |
| 路径遍历防护 | 已实现 | `manager.go:isNameSafe` 禁止 `.`、`..` 和路径分隔符 |
| SQL 注入 | 不适用 | 无 SQL 数据库 |
| WAL 文件反序列化 | 已实现 | `wal_serialize.go` 有完整的边界检查（`pos+X > len(data)`） |
| SSTable 文件 | 已实现 | Magic 校验、版本号校验、SectionTable 大小上限 64KB |
| Database/Measurement 名称验证 | 部分 | `isNameSafe` 检查存在，但未限制长度和字符集 |

### 5.2 文件权限

**当前状态**：项目使用 `os.MkdirAll`（默认 0755）和 `os.Create`/`os.OpenFile`（默认 0666）。CLAUDE.md 要求目录 0700、文件 0600。

**建议**：统一使用 `internal/storage/util.go` 中的 `SafeOpenFile` 并扩展为设置正确权限。或者创建 `SafeMkdirAll` 和 `SafeCreate` 封装。

### 5.3 资源限制

- **无连接限制**：gRPC 服务没有最大连接数限制
- **无消息大小限制**：gRPC 没有设置 `MaxRecvMsgSize`
- **无请求超时**：单次写入无超时上限
- **Shard 数量无上限**：大量 Database/Measurement 组合可能耗尽文件描述符

### 5.4 密钥管理

项目中无硬编码密钥、凭证或 token。

## 六、总结

### 6.1 优势总结

1. **架构设计成熟**：LSM-Tree 写入路径（WAL → MemTable → SSTable → Compaction）实现完整且正确
2. **双缓冲 MemTable**：写入零阻塞，异步 Flush 设计精细
3. **多种压缩编码**：覆盖时序数据类型，选择合理
4. **SID 标签编码**：核心优化，大幅减少存储开销
5. **接口解耦设计**：Shard 与 Metadata 通过接口分离，可测试性好
6. **错误处理务实**：软降级、幂等回放、panic recover
7. **并发模型正确**：锁粒度合理，死锁避免得当（如 Close 时停止 ticker 再持锁）
8. **e2e 测试丰富**：22 个场景覆盖写入、查询、compaction、WAL、恢复、持久化

### 6.2 关键改进项（按优先级排序）

| 优先级 | 改进项 | 预期收益 |
|--------|--------|---------|
| P0 | Shard.Read 全量加载改流式归并 | 消除 OOM 风险 |
| P0 | MemTable 乱序检测逻辑修复 | 防止静默数据错误 |
| P1 | Tombstone 查找 O(n) → O(log n) | Compaction 性能 |
| P1 | WriteBatch 原子性语义明确定义 | 数据一致性 |
| P1 | SSTable Write 字符串段流式读取 | 降低写入内存峰值 |
| P1 | 统一查询路径（淘汰 Shard.Read 全量加载） | 简化维护 |
| P2 | WAL checkpoint 机制 | 加速重启恢复 |
| P2 | Metrics/Telemetry 暴露 | 可观测性 |
| P2 | Compaction 配置动态调整 | 运维灵活性 |
| P2 | 文件权限符合 CLAUDE.md 要求 | 安全性 |

| P3 | magic number 常量化 | 代码质量 |

### 6.3 总体评价

Micro-TS 是一个设计良好、实现扎实的单机时序数据库。核心存储路径（写入、Flush、Compaction）的设计达到生产级别，双缓冲 MemTable、SID 编码和列式压缩等优化体现了对时序场景的深入理解。主要差距在于查询路径的内存效率、部分性能瓶颈点（Tombstone 查找、WAL Replay）和运维可观测性。补齐这些短板后，可以成为一个可靠的单机 TSDB 选型。
